基线：iOS **1.28 / 37**、Mac **0.23.1 / 36**。这是一份可逐项记录的真实首次使用检查，不以“已构建／已安装”替代交互验收。

## 如何进入首次安装状态

使用专门构建、Mac 名称带版本号的 **Chordesk First Run 0.23.1**，不要卸载日常版，也不要重置日常版的系统权限或钥匙串。测试副本使用新的应用身份、设置域、配对钥匙串、Tailscale 节点存储和目录；主机名称带“首次安装测试”。iOS Home Screen 上会与 Chordesk 同时存在。

每次需要重新从零测试，生成新的副本。只删除再安装相同身份的 iOS App 不足以保证所有凭据和授权都回到首次状态。本轮不使用该方法。

```sh
# 只准备源码及隔离清单，不签名、不启动
python3 scripts/build-first-run-qa.py --platform both --prepare-only

# 两端真实开发签名；TEAM_ID 使用你自己的开发者 Team
CHORDESK_GO=/absolute/path/to/go python3 scripts/build-first-run-qa.py --platform both --team TEAM_ID
```

默认源码、Mac 运行包和两端构建产物都位于系统临时目录。`--output` 仅改变源码／清单位置，Mac 运行包仍在临时目录；可将它移入自己的 Applications 后运行。不要从 Documents／Desktop／Downloads 运行，避免触发与远控无关的文件夹权限或同步服务的 Finder 元数据。`isolation.json` 记录实际路径与身份。脚本不自动打开 App、不批准权限、不登录账号、不发布。iOS 新身份需要对应开发配置文件；Xcode 必须有可用账号，或用 Apple Developer 生成匹配配置文件后手动签名。

如果自动签名失败，保留这一轮目录，不必生成另一个身份：用清单里的 `iosBundleID` 注册无额外 capability 的 App ID，创建 iOS App Development profile，选择已有开发证书及本轮测试设备。安装 profile 后，以清单里的 `iosDerivedData` 为构建目录，运行同一 staged project，并指定 `CODE_SIGN_STYLE=Manual`、自己的 `DEVELOPMENT_TEAM`、`CODE_SIGN_IDENTITY=Apple Development` 和匹配的 `PROVISIONING_PROFILE_SPECIFIER`。不要用其他产品的 profile、包标识或钥匙串作为替代。

**实际走一遍的顺序：**先退出日常 Mac 主机 → 打开带版本号的 Mac First Run → 点屏幕录制并按系统提示重启 → 点控制 Mac 并按提示重启 → 打开 iOS First Run → 扫描测试主机二维码 → 按下面三组检查。最后退出测试主机、回到日常 Chordesk；日常配对和账号应仍在。QA 主机使用独立动态 LAN 端口，不需要改路由器端口。

## 结果记录与发布门槛

每项用 `通过 / 失败 / 未测 / 不适用`，补充设备、系统、两端版本、网络、动作 ID 和实际提示。不要把配对码、密钥、密码、完整带令牌登录网址或私人屏幕放入公开 GitHub 报告。

本地 First Run 的独立身份能够复现新权限和空白存储，但不等同于干净机器或真正商店安装：

- Mac 发布包仍需 Developer ID 签名、公证／装订，以及从下载 → DMG → 拖拽安装 → 首开 Gatekeeper 的实际验收。
- iOS 开发签名和开发者模式并不是普通用户的 TestFlight／App Store 安装体验；正式包仍使用原生产 Bundle ID，不发布 QA 身份。
- 本轮只准备检查环境与记录，不上传 Apple、提交审核或发布安装包。新的隐私／加密申报及审核资料仍需完成。

## 0.23.1 流程修订 · 2026-11-01

用户在上一轮真实授权后确认：macOS 每项授权都提示退出重开，因此取消“先选稍后、集齐两项才统一重启”的引导。本版按上述 M02–M06 分项手动处理，不再自动连续请求或安排重启。部分权限生效可重启；服务仍要求全部生效。

本机已安装日常 Mac 0.23.1 / 35；最新隔离副本移入用户 Applications，并统一命名 **Chordesk First Run 0.23.1**。三个旧同名测试包已移入忽略入 Git 的归档目录，移除可运行 `.app` 扩展，保留恢复记录；不删除旧 TCC／钥匙串数据。最新主界面和系统权限页的两个按钮与手动重启入口已通过界面核对。此时真实两项仍待允许，完整授权和首次连接尚需复测。

旧副本从项目 Documents 中运行，用户报告首次连接会问“文稿”访问。当前采屏／输入代码没有读取个人文稿的路径；存储使用 Keychain、Application Support 或临时目录，资源在 App 内。旧运行位置是主要怀疑原因，日志没有还原该次提示的精确访问栈；不能声称已证实唯一根因。新副本不从 Documents 运行，且移除定时子进程权限预检。需再确认首次连接不出现该提示；不把文稿权限当作必需授权，也不自动授予完全磁盘访问。

### build 36 屏幕授权按钮复测

用户报告点击“允许屏幕录制”没有反应。界面确认动作已经触发，系统录屏列表存在当前 First Run，但开关关闭；控制权限已开启。旧代码忽略 `CGRequestScreenCaptureAccess()` 的返回值，缺少设置导航与明确反馈。本版请求后仍未获授权时打开录屏设置，页面导航不可用时保留普通系统设置及文字路径回退。

已原位更新同一 First Run 名称、路径、身份和签名，不新增副本；实际从系统“通用”页出发点击 App 按钮，确认进入“录屏与系统录音”，当前条目仍为关闭。未代替用户开启；原控制权限保持。16 项针对性回归通过，日常 Mac 同步安装。此次已证实的是按钮导航修复，不是屏幕权限已授予或完整首次配对已通过。
