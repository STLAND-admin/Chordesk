# 合盖恢复与传输延迟审计

2026-11-01，基于 Chordesk 当前源码及本机只读电源日志。以下区分证据、已做修正与后续方案，不代表已完成全部硬件验收。

## 合盖与键盘

本机接电 `sleep=0`、显示器自动息屏 30 分钟；本轮没有更改电源、锁屏、权限或账户。日志中有接电下的 `Clamshell Sleep`、DarkWake 与再次睡眠，说明“禁止空闲自动睡眠”不等于禁止合盖睡眠。现有 App 的 activity 也只阻止空闲系统睡眠。Apple 的闭盖外接显示器说明要求接电并使用外接键盘／鼠标：[官方排查说明](https://support.apple.com/en-us/102501)。其他远控软件的行为尚未在同条件下复现，不能推断其采用了哪一种保活方式。

源码发现两个不同环节：

1. `LANHost.tick()` 原先发现当前显示器 offline 就调用 `stop()`，同时关闭配对监听和 Tailscale 转发。内置屏合盖离线有可能走到此分支，即使系统尚未彻底睡眠也会失去服务。Mac 0.20.1 改为暂停输入并保留服务，只恢复原共享显示器；不会暗中共享另一块屏幕。
2. `willSleep`／会话失活会释放输入、清理焦点并撤销本次控制；这是保留的权限边界。唤醒后要重连，不能仅凭恢复一帧旧画面重新授权。已认证 hello 才能请求远程用户活动；系统真正睡眠、无法执行网络接收时，App 本身的这条代码不会运行。

屏幕捕获用户停止 `-3817`、系统停止 `-3821`、权限拒绝仍停止服务。只有明确的缺少捕获源错误、原显示器离线且权限有效才保留等待。新画面还需原会话、捕获版本和控制许可核验；系统睡眠或显示器仍离线时丢弃到达的帧。

**2026-11-01 用户补充：**接电合盖后多为连接超时，偶尔能看到锁屏；UU 显示在线。键盘异常明确为 Mac 锁屏密码无法输入。当前硬件只读查询仅见内置显示器；未改变电源或安全设置。

**锁屏输入仍未定因。** 当前文字提交前查焦点，再使用 CGEvent Unicode 事件；特殊按键走虚拟键码。睡眠／会话失活会撤销控制，画面恢复不等于输入许可恢复。也不能由 `CGEvent.post` 返回就断言 loginwindow 接受了文字。公开 `kCGSessionOnConsoleKey` 只报告 GUI 会话位置，不作为精确锁屏检测；没有读取未公开的锁屏键、密码框内容或 TCC 数据库。

Mac 0.21.0 在睡眠／会话切换及唤醒时释放本应用输入并重建自己的 private CGEventSource，不向整个系统补发修饰键松开，不自动恢复已撤销控制；按键诊断移除实际键值。它是会话输入状态清理，**不能当成锁屏密码问题已修复**。需要用户先在开盖、仅锁屏的条件下重连，记录画面与控制许可，再与合盖结果比较。密码只由用户在其 Duo 自行输入，不采集、记录或代输。

Apple 的 [CGEventSource](https://developer.apple.com/documentation/coregraphics/cgeventsource) 和[会话属性](https://developer.apple.com/documentation/coregraphics/window-server-session-properties)文档并不保证任意当前用户进程都能完成锁屏登录。其他产品也有各自的锁屏输入实现与故障，不能直接推断必须安装 root daemon，或宣称公开 API 一律不可能实现。当前尚未增加系统级 helper／后台 daemon。

下一轮记录：接电／电池、外接屏有无、共享屏 ID 是否在线、合盖后的离线还是黑屏、Mac 状态提示、唤醒后重新点选输入框是否恢复。再与 UU 在同样条件下对照。无需先改系统安全设置或恢复已弃用的虚拟屏方案。

## 当前编码和延迟候选

当前是 **ScreenCaptureKit → 完整画面 JPEG → TLS 有序字节流 → iPhone JPEG 解码显示**，不是 H.264／HEVC，也不是 RDP。默认 `.efficient` 是最长边 1280 像素、JPEG 65%、请求上限 15 fps；保留用户已有选择，实际 Mbps 随内容变化。

- 15 fps 的帧间隔约 66.7 ms，理想情况下仅等待下一帧平均就约 33 ms；这不是已测得的端到端延迟。
- 每帧独立压缩，没有 H.264 的帧间预测；动态页面带宽可能较高。采集 queueDepth 为 3，编码串行执行。
- 发送端超过 512 KiB pending bytes 后才丢弃可丢视频帧；系统网络缓冲和链路中仍可有数据。仅作算例：512 KiB 在 4 Mbps 上约需 1.05 秒，不代表本次实测积压就是这个数值。
- 手机在连接回调中同步解码 JPEG，再提交到主线程；过时画面与后续状态处理可能排队。输入的反向网络方向不能简单等同于被下行视频完全阻塞，但主线程、解码和排队仍需测量。
- 当前没有分阶段耗时与画面呈现 ACK，不能把延迟全部归因于 Tailscale，也未核实本次连接究竟是 P2P direct 还是 relay。

## 优化顺序（尚未更换编码）

1. **先加测量**：采集时间、编码耗时、待发字节、RTT、收到／解码／显示时间、丢帧和 direct／relay。比较同局域网与蜂窝、静止文字与滚动网页，报告 P50/P95，不把接收 fps 当显示 fps。
2. **减少陈旧帧**：采集／编码／待发／解码每段限制积压，只保留最新待处理帧；已经提交 TCP 的字节无法撤回，因此要在入队前限流。再评估独立控制和视频通道，沿用配对认证、顺序与释放检查。
3. **VideoToolbox 硬件 H.264**：实时、无帧重排、低延迟码率控制，先 720p/30 和 720p/60，对比当前 JPEG；动态调整目标码率，重连或切屏发送关键帧。Apple 提供专门的低延迟 H.264 硬件模式：[VideoToolbox 官方说明](https://developer.apple.com/videos/play/wwdc2021/10158/)。保留能力协商和 JPEG 回退，不承诺某个固定时延。
4. **再评估传输协议**：弱网中有序可靠流会受丢包重传影响；如硬编码和队列优化仍不足，再评估 WebRTC／数据报视频与拥塞控制，不直接放宽公网地址或认证边界。

无需等 RDP 才能降低延迟。单纯提高分辨率或码率可能加重网络积压；仅把 15 fps 改成 60 fps 也未必更快。当前本地更新不悄悄改变用户选择的省流档位。

## 可达状态检查（1.26 / Mac 0.21.0）

手机“连接 Mac”的已配对列表新增一次性检查：显示服务在线、用户会话暂不可用、显示器暂不可用、已有设备连接，或暂时无法连接，并标注检查时间。只有原配对 PSK 的 TLS 验证、随机请求标识及原 hostID 校验通过才显示在线；本机 Tailscale Ready 不能证明另一台 Mac 在线。查询不发送 hello、不请求唤醒、不调整分辨率、不打开控制、不占用正在使用的远控连接。

旧主机没有这个只读协议，因此需要先正常连接新版一次，由认证状态保存支持能力；不主动探测旧主机，避免其把查询当成真实配对。打开配对列表自动检查一次，也可手动刷新；逐台查询、每台最多等待 12 秒，关闭列表／退后台／换模式／开始远控即取消，没有常驻后台轮询。超时不是“关机”证据，也可能是主机服务停止、地址改变或网络不可达。
