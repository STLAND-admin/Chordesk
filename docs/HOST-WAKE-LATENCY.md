# 合盖恢复与传输延迟审计

2026-11-01，基于 Chordesk 当前源码及本机只读电源日志。以下区分证据、已做修正与后续方案，不代表已完成全部硬件验收。

## 合盖与键盘

本机接电 `sleep=0`、显示器自动息屏 30 分钟；本轮没有更改电源、锁屏、权限或账户。日志中有接电下的 `Clamshell Sleep`、DarkWake 与再次睡眠，说明“禁止空闲自动睡眠”不等于禁止合盖睡眠。现有 App 的 activity 也只阻止空闲系统睡眠。Apple 的闭盖外接显示器说明要求接电并使用外接键盘／鼠标：[官方排查说明](https://support.apple.com/en-us/102501)。其他远控软件的行为尚未在同条件下复现，不能推断其采用了哪一种保活方式。

源码发现两个不同环节：

1. `LANHost.tick()` 原先发现当前显示器 offline 就调用 `stop()`，同时关闭配对监听和 Tailscale 转发。内置屏合盖离线有可能走到此分支，即使系统尚未彻底睡眠也会失去服务。Mac 0.20.1 改为暂停输入并保留服务，只恢复原共享显示器；不会暗中共享另一块屏幕。
2. `willSleep`／会话失活会释放输入、清理焦点并撤销本次控制；这是保留的权限边界。唤醒后要重连，不能仅凭恢复一帧旧画面重新授权。已认证 hello 才能请求远程用户活动；系统真正睡眠、无法执行网络接收时，App 本身的这条代码不会运行。

屏幕捕获用户停止 `-3817`、系统停止 `-3821`、权限拒绝仍停止服务。只有明确的缺少捕获源错误、原显示器离线且权限有效才保留等待。新画面还需原会话、捕获版本和控制许可核验；系统睡眠或显示器仍离线时丢弃到达的帧。

**2026-11-01 用户补充：**接电合盖后多为连接超时，偶尔能看到锁屏；UU 显示在线。键盘异常明确为 Mac 锁屏密码无法输入。当前硬件只读查询仅见内置显示器；未改变电源或安全设置。

**锁屏输入仍未定因。** 当前文字提交前查焦点，再使用 CGEvent Unicode 事件；特殊按键走虚拟键码。睡眠／会话失活会撤销控制，画面恢复不等于输入许可恢复。也不能由 `CGEvent.post` 返回就断言 loginwindow 接受了文字。公开 `kCGSessionOnConsoleKey` 只报告 GUI 会话位置，不作为精确锁屏检测；没有读取未公开的锁屏键、密码框内容或 TCC 数据库。

Mac 0.21.0 在睡眠／会话切换及唤醒时释放本应用输入并重建自己的 private CGEventSource，不向整个系统补发修饰键松开，不自动恢复已撤销控制；按键诊断移除实际键值。它是会话输入状态清理，**不能当成锁屏密码问题已修复**。需要用户先在开盖、仅锁屏的条件下重连，记录画面与控制许可，再与合盖结果比较。密码只由用户在其 Duo 自行输入，不采集、记录或代输。

Apple 的 [CGEventSource](https://developer.apple.com/documentation/coregraphics/cgeventsource) 和[会话属性](https://developer.apple.com/documentation/coregraphics/window-server-session-properties)文档并不保证任意当前用户进程都能完成锁屏登录。其他产品也有各自的锁屏输入实现与故障，不能直接推断必须安装 root daemon，或宣称公开 API 一律不可能实现。当前尚未增加系统级 helper／后台 daemon。

下一轮记录：接电／电池、外接屏有无、共享屏 ID 是否在线、合盖后的离线还是黑屏、Mac 状态提示、唤醒后重新点选输入框是否恢复。再与 UU 在同样条件下对照。无需先改系统安全设置或恢复已弃用的虚拟屏方案。

## 1.27 / Mac 0.22 编码与测量

默认路径改为 **ScreenCaptureKit → VideoToolbox 实时 H.264 → 原 TLS 有序字节流 → VideoToolbox 解码 → CGImage 显示**。协商能力，旧客户端／主机及硬件失败回退原 JPEG；手机设置可关闭优先 H.264。默认仍省流 15 fps、最长边 1280、H.264 目标 1.5 Mbps；已有画质保留，不承诺固定码率或请求帧数全部达标。

硬件编码启用实时、无帧重排和低延迟码率控制；单输入完成后再处理下一输入。帧间依赖以流 ID、序号、SPS/PPS 和 IDR 恢复：待发视频未完成时丢弃新帧，丢弃依赖帧后等待新关键帧；客户端序列缺口会限频请求关键帧，解码失败请求 JPEG。发送端最多一个应用层视频写入未完成，但 TCP／系统网络缓冲不等于空，不能据此承诺没有排队延迟。保留 4 MiB 包长和像素上限。

左上统计是实际图像像素、视频包接收 fps／载荷 Mbps、实际编码与路径、nonce 匹配的应用 RTT。RTT 不等于输入→Mac执行→采集→编码→解码→显示的完整延迟；未知时显示横线，不推测。静止画面没有更新时 fps 降低正常，接收不代表屏幕实际刷新。

Mac 上生成图像的真实硬件编码／解码、缺帧恢复与流重建测试通过；尚没有同场景真机 JPEG/H.264 时延、清晰度或功耗对比。仍需测量分阶段耗时、Tailscale direct／relay 以及主线程呈现积压；后续可比较直接视频图层／Metal 呈现与独立视频通道。15 fps 帧间隔约 66.7 ms，这部分不能靠 H.264 消除。120／144 fps 仍为实验请求上限。

依据：[Apple 低延迟 H.264 硬件模式](https://developer.apple.com/videos/play/wwdc2021/10158/)。实现与验收见 [1.27 验证](DEVELOPMENT-HISTORY.md#archive-validation-1-27)。

## 锁屏二次重连反馈与修正

用户在 1.26 确认配对状态检查正常；开盖接电仅锁屏时，第一次能看到画面且输入有反应，第二次不行。这比合盖更容易隔离，不能归因为一定发生整机睡眠，也不能确认 TCC 被撤销。

代码候选路径：断连恢复显示模式会清空最后画面；静态锁屏可能只产生 idle 而非 complete 帧，等待新画面的控制恢复因此不继续。0.22 在已认证新会话中请求有界重建原共享流；若旧会话正在恢复模式，等其结束再重试。等待新帧仍保持控制暂停。恢复显示模式遇到明确可恢复捕获错误时保留监听，人工／系统停止和权限撤销仍停止。**该修正未获锁屏连续两次重连的真机确认**；没有自动输入密码、修改安全设置或增加系统 helper。

## 可达状态检查（1.26 / Mac 0.21.0）

手机“连接 Mac”的已配对列表新增一次性检查：显示服务在线、用户会话暂不可用、显示器暂不可用、已有设备连接，或暂时无法连接，并标注检查时间。只有原配对 PSK 的 TLS 验证、随机请求标识及原 hostID 校验通过才显示在线；本机 Tailscale Ready 不能证明另一台 Mac 在线。查询不发送 hello、不请求唤醒、不调整分辨率、不打开控制、不占用正在使用的远控连接。

旧主机没有这个只读协议，因此需要先正常连接新版一次，由认证状态保存支持能力；不主动探测旧主机，避免其把查询当成真实配对。打开配对列表自动检查一次，也可手动刷新；逐台查询、每台最多等待 12 秒，关闭列表／退后台／换模式／开始远控即取消，没有常驻后台轮询。超时不是“关机”证据，也可能是主机服务停止、地址改变或网络不可达。


## 最新反馈与合盖证据（Mac 0.22.1）

用户澄清开盖锁屏正常，问题是合盖后短暂连上、键盘出现后整体卡住，LAN／Tailscale 均如此。最新电源日志确认接电状态仍出现 Clamshell Sleep，短暂 Full Wake 后重入 Dark Wake／睡眠；单纯改编码无法修复系统睡眠。

新增只在接电、已认证活动会话且原防睡眠偏好开启时的 NetworkClientActive 请求，断连／拔电／停止即释放。公开 IOPMLib.h 说明它可保持 Dark Wake 的 CPU、磁盘和网络，但不保证 framebuffer／GPU；系统仍可忽略请求。现有远程用户活动请求保留，不模拟密码／输入，也不安装系统 helper。158 项回归通过，已部署 Mac 0.22.1，用户复测仍失败：不输入密码也会卡住／断开。日志显示持有 NetworkClientActive 时仍重入 Dark Wake／睡眠，因此不把回车视为必要触发条件。[验证记录](DEVELOPMENT-HISTORY.md#archive-validation-1-27)

## 后续编码选择

2026-11-01 本机 M4 Pro 的 VideoToolbox 枚举显示 H.264、HEVC 硬件编码器，未列 AV1 编码器；三者均报告硬件解码能力。1.28 / Mac 0.23.0 已加入可选 HEVC，与 H.264 共用硬件编解码和有界队列；不能把支持播放 AV1 当成能硬件编码 AV1。

Apple 在文件编码场景给出 HEVC 相比 H.264 同等视觉质量下体积最多降低 40% 的参考；Meta 在视频点播说明中给出 AV1 相比 HEVC／VP9 约 30% 的编码效率优势。这些不是 Chordesk 实时桌面基准，不能直接套到低码率文字、无重排编码或推导延迟同比减少。[Apple HEVC](https://support.apple.com/en-la/101939) · [Meta AV1](https://engineering.fb.com/2023/02/21/video-engineering/av1-codec-facebook-instagram-reels/)

输入上行、Mac 处理／等帧、编码、视频下行、解码与呈现共同组成感知延迟，排队存在于各段。Tailscale 直连通常比中继低延迟，但当前尚未测定本次 direct／relay。RTT 也包含应用调度与共用流排队，不应与这些重复相加。[Tailscale 连接类型](https://tailscale.com/docs/reference/connection-types)

默认保持 H.264 / 省流 15 fps；1.28 可选 H.265（HEVC），当前目标为相同画质档 H.264 预算的 75%（省流 1.125 Mbps），是初始参数，不是同等画质保证。两种格式的本机真实硬件编码／解码、丢帧恢复和互切测试通过；尚待 Duo 及公网实测清晰度、耗时和耗电。AV1 按用户要求不实现／不测试。
